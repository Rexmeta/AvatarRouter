# AvatarRouter 바이브 코딩 개발 지시서

**개발 목표:** 독립적인 `AvatarRouter` 서비스를 구축하고, 기존 RoleplayX에 플러그인 형태로 연결합니다. 사용자는 RoleplayX에서 원하는 실시간 AI 아바타를 선택하고, 기존 시나리오·페르소나·대화·평가 기능을 그대로 사용할 수 있어야 합니다.

개발 방식은 **LiveKit Agents의 기존 아바타 플러그인을 최대한 재사용하는 것**입니다. WebRTC, 영상 스트리밍, 립싱크 등 이미 구현된 기술을 다시 개발하지 않습니다.

아래 내용은 Replit Agent나 Codex에 전달할 수 있도록 구성했습니다. 먼저 프로젝트 전체 개발 지시서를 입력하고, 이후 단계별 프롬프트를 순서대로 실행하는 방식입니다.

## 1. 확정할 기술 방향

| 구분 | 결정 |
|---|---|
| 프로젝트 | `AvatarRouter` — 독립 저장소 |
| 핵심 프레임워크 | LiveKit Agents |
| API 서버 | Node.js + TypeScript |
| 아바타 실행 | Node.js Worker + Python Worker |
| 웹 UI | React + TypeScript |
| 데이터베이스 | PostgreSQL |
| 실시간 전송 | LiveKit WebRTC |
| 초기 공급자 | Anam, Tavus, LemonSlice, Simli |
| 첫 연동 대상 | 기존 RoleplayX |
| 연동 방식 | REST API + TypeScript SDK + React 컴포넌트 |
| 인증 | 서버 발급 단기 세션 토큰, 공급자 키는 서버 보관 |
| 초기 배포 | Docker 기반 독립 서비스 |

**MVP 성공 조건:** AvatarRouter 단독 Playground에서 외부 아바타가 작동하고, RoleplayX에서도 동일한 아바타를 선택해 기존 AI 대화 및 평가를 완료할 수 있어야 합니다.

공식 기술 참고자료는 [LiveKit Avatar Plugins](https://docs.livekit.io/agents/models/avatar/?utm_source=chatgpt.com), [LiveKit Agents GitHub](https://github.com/livekit/agents?utm_source=chatgpt.com), [LiveKit Agents JS](https://github.com/livekit/agents-js?utm_source=chatgpt.com)입니다.

## 2. 개발 착수 전 확인할 사항

현재 연결된 GitHub 저장소의 README를 다시 확인했습니다.

[RoleplayBot 저장소](https://github.com/Rexmeta/RoleplayBot?utm_source=chatgpt.com)에는 React·Node.js·Gemini Live 기반의 롤플레잉과 평가 기능이 명시되어 있습니다. 반면 [ContentX 저장소](https://github.com/Rexmeta/ContentX?utm_source=chatgpt.com)는 ContentX를 시뮬레이션 작성 엔진, RoleplayX를 AI Agent 품질 검증 인프라로 설명합니다.

따라서 **RoleplayX라는 이름만 보고 연동 대상을 추정해서는 안 됩니다.** 실제 운영 서비스의 저장소와 대화 실행 경로를 확인한 다음 플러그인을 연결해야 합니다.

아래 프롬프트에는 이 확인 작업도 포함했습니다.

# 3. 마스터 프롬프트 — 전체 프로젝트 개발 지시

다음 내용을 **새로운 AvatarRouter 프로젝트의 Replit Agent 또는 Codex에 그대로 입력**하세요.

# PROJECT: AvatarRouter

## 1. Mission

Build an independent, production-oriented, provider-agnostic real-time AI avatar routing platform named AvatarRouter.

AvatarRouter must allow developers and applications to discover, connect, render, switch between sessions, monitor, and manage multiple live AI avatar providers through a unified API and SDK.

The first integration target is the existing RoleplayX service.

AvatarRouter must also run independently, without RoleplayX.

The goal is NOT to build a new avatar-generation model or implement WebRTC from scratch.

Reuse existing open-source infrastructure, particularly LiveKit Agents and its official avatar provider plugins.

## 2. Mandatory preliminary investigation

Before writing code:

1. Inspect the latest official LiveKit Agents documentation.
2. Inspect the current LiveKit Agents JavaScript and Python repositories.
3. Confirm the currently supported avatar providers and their installation requirements.
4. Verify the SDK signatures against the installed package versions.
5. Review the current repositories:
   - github.com/Rexmeta/RoleplayBot
   - github.com/Rexmeta/ContentX
6. Identify which repository and deployment actually power the existing RoleplayX user-facing service.
7. Locate the existing avatar rendering, Gemini Live audio pipeline, conversation persistence, persona configuration, and evaluation integration.
8. Produce an architecture compatibility report before modifying the existing service.

Do not assume that README documentation accurately reflects every implementation detail.

Do not modify the existing RoleplayX service during the initial AvatarRouter development phase.

## 3. Architecture

Create a standalone monorepo:

AvatarRouter/
  apps/
    api/
    studio/
    worker-node/
    worker-python/
  packages/
    core/
    sdk/
    react/
    provider-contract/
    roleplayx-plugin/
  infrastructure/
    docker/
    migrations/
  docs/
  examples/
  tests/

Use:

- TypeScript and Node.js for the API.
- React and TypeScript for the web application.
- Python only where official avatar integrations require it.
- PostgreSQL for persistent data.
- LiveKit for real-time media and agent transport.
- Docker for local and production deployment.
- Zod for API validation.
- OpenAPI for API documentation.

Start with a modular monolith, not microservices.

Use separate workers only where required by runtime or language constraints.

## 4. Provider strategy

Initial target providers:

1. Anam
2. Tavus
3. LemonSlice
4. Simli

Implement Anam and Tavus first.

Use existing official LiveKit plugins wherever possible.

Do not reimplement existing avatar SDKs.

Implement a provider registry with capability metadata.

Support:

- Provider discovery
- Avatar listing
- Avatar selection
- Session creation
- Session termination
- Connection status
- Usage tracking
- Provider errors
- Provider-specific configuration
- Capability detection

Provider integrations must be independently enableable or disableable.

Unavailable credentials must not prevent the platform from starting.

Do not fabricate avatar availability, pricing, or provider capabilities.

## 5. Separation of responsibilities

AvatarRouter owns:

- Avatar catalog
- Provider adapters
- Avatar session lifecycle
- Real-time media integration
- Connection management
- Usage metering
- Provider configuration
- Operational monitoring

RoleplayX owns:

- Scenarios
- Personas
- AI dialogue
- Conversation policy
- Assessment
- Feedback
- User progress

AvatarRouter must not require scenario IDs, competency rubrics, or RoleplayX-specific database models.

Allow optional opaque application metadata for tracing and integration.

## 6. Unified API

Design and implement:

GET /v1/providers
GET /v1/providers/:id/capabilities
GET /v1/avatars
GET /v1/avatars/:id
POST /v1/sessions
GET /v1/sessions/:id
POST /v1/sessions/:id/end
GET /v1/sessions/:id/usage
GET /v1/usage
GET /health
GET /ready

Use application-scoped authentication and tenant isolation.

Session creation must return only client-safe connection information.

Never expose provider API secrets to the browser.

## 7. Core provider contract

Define a provider adapter interface that supports:

- getCapabilities()
- listAvatars()
- validateConfiguration()
- createSession()
- terminateSession()
- getUsage()

Do not force all providers to implement unsupported features.

Use explicit capability flags.

Support at least these modes:

- static
- renderer
- full_stack
- hybrid

The system must distinguish avatar rendering from conversation generation.

## 8. Frontend Studio

Create a responsive web application with:

### Explore
Browse providers and avatars.

### Playground
Select an avatar and start a real-time session.

### Connect
Configure provider credentials and obtain SDK integration instructions.

### Sessions
Inspect active and completed sessions.

### Usage
View session duration, provider, estimated cost, and errors.

Use clean enterprise-oriented UI.

Display connection status and actionable errors.

Support Korean and English UI localization.

## 9. RoleplayX integration

Create:

@avatar-router/sdk
@avatar-router/react
@avatar-router/roleplayx-plugin

The RoleplayX plugin must provide:

- Avatar selection
- Session start and end
- Live avatar rendering
- Connection state
- Event callbacks
- Transcript synchronization where supported
- Usage reporting
- Graceful fallback to the existing static avatar

Preserve the existing Gemini Live conversation pipeline whenever technically feasible.

Do not silently replace Gemini Live with a new LLM or TTS provider.

First implement a proof of concept demonstrating that existing RoleplayX-generated speech can drive a LiveKit avatar.

If the selected provider requires a different conversation architecture, report the limitation and provide a compatible alternative.

## 10. Security

Implement:

- Server-side provider credentials
- Secret encryption or external secret storage
- Short-lived client tokens
- Tenant isolation
- Role-based administrative access
- API rate limiting
- Session expiration
- Webhook authentication where applicable
- Structured audit logging
- No secrets in frontend bundles or logs

Never commit credentials.

## 11. Usage and cost tracking

Track:

- Provider
- Avatar
- Tenant
- Application
- Session
- Connection duration
- Billable duration when available
- Session start/end
- Errors
- Estimated provider cost
- Actual provider cost when available

Separate estimated costs from confirmed billed costs.

Do not treat connected time as billable time unless the provider's billing rules justify it.

## 12. Testing

Implement:

- Unit tests for provider contracts
- Mock-provider integration tests
- API authentication tests
- Tenant-isolation tests
- Session lifecycle tests
- Failure recovery tests
- Browser UI smoke tests
- Real-provider smoke tests when credentials exist

All tests must run without paid provider credentials by using mocks.

## 13. Development principles

- Reuse existing LiveKit integrations.
- Avoid unnecessary abstractions.
- Avoid premature microservices.
- Keep the public API stable.
- Use feature flags.
- Implement structured logging.
- Write migration scripts.
- Maintain a clear README.
- Provide a working Docker Compose environment.
- Do not claim untested provider integrations are complete.

## 14. Definition of Done

The initial MVP is complete only when:

1. AvatarRouter runs independently.
2. The Studio is accessible.
3. At least two real avatar providers work end-to-end.
4. A third and fourth provider can be added through adapters.
5. The TypeScript SDK works.
6. The React component works.
7. RoleplayX can use an external avatar without breaking existing dialogue and assessment behavior.
8. Provider usage is recorded.
9. Errors and fallback behavior are tested.
10. Deployment and integration instructions are documented.

## 15. Required output

Before implementation, provide:

1. Current repository analysis
2. LiveKit integration compatibility matrix
3. Proposed architecture
4. Database schema
5. API contracts
6. Development milestones
7. Known technical risks

Then implement incrementally.

At the end of each milestone, report:

- Files changed
- Features completed
- Tests executed
- Test results
- Known limitations
- Next milestone

Do not mark a milestone complete without running its tests.

# 5. 반드시 먼저 해결할 기술 문제

개발 일정에 가장 큰 영향을 줄 부분은 **기존 Gemini Live와 LiveKit AvatarSession의 결합**입니다.

LiveKit의 일반적인 아바타 연동은 다음 구조를 가정합니다.

```text
사용자 음성
    ↓
LiveKit AgentSession
    ↓
AI 대화 및 음성 생성
    ↓
AvatarSession
    ↓
실시간 아바타
```

반면 현재 RoleplayBot README의 설명대로라면 기존 실시간 대화는 Gemini Live 중심입니다.

```text
사용자 음성
    ↓
Gemini Live
    ↓
AI 음성 응답
    ↓
기존 RoleplayX 화면
```

따라서 목표 구조는 다음과 같습니다.

```text
                   RoleplayX
                       │
                 Gemini Live
                       │
                AI Audio Output
                       │
                Audio Bridge
                       │
                AvatarRouter
                       │
              LiveKit AvatarSession
                       │
                Live Avatar
                       │
                    사용자
```

**Audio Bridge는 실제 SDK를 확인하기 전까지 구현 가능성이 확정된 기능으로 취급하면 안 됩니다.**

특히 PCM 형식, 샘플레이트, 스트리밍 단위, 턴 종료 신호, 끼어들기 처리, 에코 방지 등을 확인해야 합니다.

이 부분을 Phase 1의 핵심 기술 검증에 추가하는 것이 좋습니다.

### 추가 프롬프트: Gemini Live 호환성 검증

Perform a focused technical spike for connecting the existing RoleplayX Gemini Live audio output to LiveKit avatar rendering.

Investigate:

1. Current Gemini Live audio output format.
2. Sample rate and encoding.
3. LiveKit AgentSession audio input/output contracts.
4. AvatarSession audio forwarding requirements.
5. Whether an existing LiveKit Gemini integration can be reused.
6. Whether the existing RoleplayX Gemini Live session can be preserved.
7. Interruption and turn-taking synchronization.
8. Transcript synchronization.
9. Latency overhead.
10. Echo and audio feedback prevention.

Compare two architectures:

A. Preserve the existing Gemini Live session and bridge audio into LiveKit.

B. Move the Gemini Live conversation runtime into a LiveKit-compatible agent while preserving RoleplayX business logic.

Recommend the architecture with the lowest regression risk and acceptable latency.

Implement a minimal proof of concept before changing production code.

Do not claim compatibility without a working end-to-end test.

## 7. 실제 개발 진행 순서

**권장 순서는 다음과 같습니다.**

**첫째, AvatarRouter 신규 프로젝트를 생성하고 마스터 프롬프트를 입력합니다.** 기존 RoleplayX 코드는 아직 수정하지 않습니다.

**둘째, Phase 1과 Gemini Live Audio Bridge 검증을 진행합니다.** 이때 Anam 또는 Tavus의 실시간 아바타가 기존 AI 음성으로 정상 작동하는지 확인합니다.

**넷째, Phase 3과 Phase 4를 진행합니다.** LemonSlice·Simli를 추가하고 RoleplayX에 플러그인으로 연결합니다.

**다섯째, Phase 5와 Phase 6을 진행합니다.** 독립 Studio와 운영 관리 기능을 완성합니다.

> AvatarRouter는 독립적으로 실행되어야 하고, RoleplayX는 플러그인을 설치하는 것만으로 여러 Live Avatar를 사용할 수 있어야 한다. 기존 RoleplayX의 AI 대화와 평가 기능은 변경하지 않는다.

이 기준을 중심으로 개발하면 **실시간 아바타 통합 → RoleplayX 서비스 적용 → 독립 Avatar Hub 사업 확장**이라는 목표를 단계적으로 달성할 수 있습니다.
